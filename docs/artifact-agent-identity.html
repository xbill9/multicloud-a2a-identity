Cross-Cloud A2A

Why SPIRE Doesn't Fit Multicloud Agents

The A2A protocol is not what limits a multi-Cloud Agent mesh. Auth is. The advice you will get is to adopt SPIFFE and SPIRE — and on a deployed three-Cloud mesh that advice turns out to be answering a different question than the one being asked.

The Protocol is the Easy Part

A2A does what it says. Cards resolve, tasks come back, and client libraries in three languages talk to each other without special cases. Across the benchmark series the timings tracked the remote model and runtime — never anything in the wire format. There is no protocol work left to do to run Agents on three Clouds.

Auth is where it stops, and it stops hard. Every cross-Cloud call needs a credential the far side will accept, and the far side is a different vendor with a different notion of what acceptable means. A2A is deliberately silent here: the spec has the client read the scheme off the Agent Card and get the credential out of band. Out of band is doing a lot of work in that sentence. It is the entire integration.

Ask what to do about that and you will be pointed at SPIFFE and SPIRE. Jitendra Gupta's article on Agent identity is a well-argued version of the case, and the recommendation is common enough now to count as the default answer.

I do not think it is the right answer for this problem, and after deploying the mesh I think I can say why in one word.

Multicloud Means Two Different Things

The word is doing double duty, and the two meanings have almost nothing in common except the adjective.

Meaning A — what SPIRE is for

My workloads, spread across Clouds

You own the compute. Clusters on EKS, GKE and AKS, one organisation, one administrative boundary drawn around all of it.

  • You control the nodes
  • You choose the identity format
  • Both ends of every call are yours
  • One trust domain is a coherent idea
Meaning B — what an Agent mesh is

My Agent, calling other vendors' services

You own one end. The others are managed runtimes — Bedrock AgentCore, Azure Container Apps, Cloud Run — each with its own idea of a valid caller.

  • You control no nodes
  • Each far end dictates the format
  • Only the calling end is yours
  • There are three trust domains and you administer one

SPIFFE was built for the first one. It is a way to give identity to workloads inside a boundary you control, and it is good at that. An Agent mesh is the second one, where the hard part is that the far end is not yours and never will be.

That is the confusion. "SPIFFE is good for multicloud" is true of meaning A and gets repeated as though it were true of meaning B. But the difficulty in meaning B is not that your workloads lack an identity. It is that three vendors each have their own rules about which identities they will accept, and no identity format you adopt changes that.

What the Framework Already Runs

The coordinator runs on Cloud Run and calls three Agents. Every leg starts at the same place — the metadata server issues a short-lived OIDC token with whatever audience you ask for — then diverges by Cloud:

GCP → GCP Google ID token, audience pinned to the service URL
GCP → AWS Token to STS AssumeRoleWithWebIdentity, then SigV4
GCP → Azure Token to an Entra Federated Identity Credential

No stored secrets anywhere on those legs. Each has a positive control and a negative control — run it as deployed, then run it with the credential removed and confirm it is refused. Eight probes, all holding on the current build.

The Clouds Already Ship the SVID

Here is the first thing that makes the recommendation odd. The credential at the start of all three legs is a short-lived, audience-scoped JWT that the platform issues, the platform signs, and the workload cannot forge or extract.

That is a JWT-SVID in everything but the namespace. And the attestation behind it is stronger than anything you can install, because the attester is the runtime — there is no agent inferring what a workload is from process metadata, because the platform already knows.

So on managed runtimes, SPIRE's headline deliverable is something the Cloud hands you for nothing.

What Does a Google Identity Even Mean to AWS?

Worth stopping on, because the answer is less than most diagrams imply, and it explains everything that follows.

When the coordinator presents a Google-signed token to STS, AWS does two things. It fetches Google's public keys from a well-known OIDC discovery endpoint and checks the signature. Then it applies the conditions you wrote into the role's trust policy — this audience, this subject.

That is the whole mechanism. AWS learns that a token was signed by whoever holds a key Google published, and that the token says sub is some number. It has no idea what that number is. It has never heard of your service account, your project, or your Agent.

Authentication crosses the boundary. Authorization never does. The number in that token means precisely what your trust policy says it means, and nothing else. Delete the condition and the same valid token authorizes nothing.

Which means there is no such thing as a cross-Cloud identity. There is a locally defined mapping, at each far end, from a foreign signature to a local principal. Three far ends, three mappings.

That reframes the pinning problem. Writing the identity down three times is not a symptom of doing federation without SPIFFE — it is what a trust boundary is. Each side has to decide for itself what a foreign identity is allowed to do, because nobody else can decide it for them.

SPIRE does not change that. It changes whose signature is on the token. AWS still has to be told that spiffe://example.org/coordinator may assume a role, Entra still has to be told the same thing in its own format, and both mappings still live on their side of the wall. One issuer, still three mappings.

And what does it mean on Cloud Run?

The same question turned inward is more uncomfortable, and it is the one that changed how I read all of this.

That identity belongs to the service account, which is attached to the service. Not to a revision, not to a container instance, not to a request. So the token proves:

  • Something running as this service account asked for it.

That is the entire claim. It does not distinguish one revision from the next, so a rollback or a bad image carries the same identity as the version you reviewed. It does not distinguish concurrent requests, so every caller inside the container shares it. And it does not distinguish callers at all — anything that can get code to run in that container gets the full weight of it.

That is not hypothetical here. Reviewing this project for these articles turned up its coordinator open to the internet on a public invoker binding. For as long as that was true, an anonymous request arrived and was served by a container holding federated credentials for three Clouds. The identity behaved perfectly throughout. It was never designed to answer the question that mattered.

Workload identity answers "what is running", and it answers it at the granularity of a deployment. It does not answer "which version", "which request", or "on whose behalf". Google's does not, and neither does a SPIFFE ID — workload attestation can pin a binary or a pod, which is finer, but it still describes the workload rather than the work.

So the gap that matters is not on the axis anybody is arguing about. Swapping one workload identity system for another moves you along an axis you are already fine on.

And there is no fixed node underneath any of it. A Cloud Run instance is created for a burst of traffic and destroyed, the service scales to zero between runs, and the next request may be served by something that did not exist a second earlier. Nothing about that container is durable enough to be an identity.

So the substrate is pulling in two directions at once, and both of them break SPIRE's model. The identity is too coarse — one service account shared by every revision and every request. The compute is too fluid — no stable node to attest in the first place. SPIRE needs a durable node it can vouch for, then an agent living on it long enough to vouch for the workloads above. Serverless offers neither half.

On a substrate with no fixed node, the platform is the only party that can attest anything. It is the only one that knows which image is running, in which revision, under which service account, at the instant the token is minted. No agent you install can observe that, because there is nowhere to install it and nothing stable to observe.

Which makes the managed metadata server not merely the convenient attester on this substrate. It is close to the only sound one.

SPIRE Does Not Remove the Federation Work

This is the row people skip when they cost it out.

Every Agent in this mesh consumes external OIDC and carries on doing so. AWS still needs a trust policy. Entra still needs a federated credential. Cloud Run still needs an invoker binding. SPIRE changes which issuer those three trust — it does not reduce their number, and configuring them is the work.

It also changes the shape of that configuration in a way worth knowing about. Google is a native AWS identity provider, so you must not create an IAM OIDC provider for it:

"Principal": { "Federated": "accounts.google.com" },
"Condition": { "StringEquals": {
    "accounts.google.com:oaud": "sts.amazonaws.com",
    "accounts.google.com:sub":  "<service account numeric ID>"
}}

SPIRE is not native, so the IAM OIDC provider becomes required, and the conditions key on a discovery domain you host:

"Principal": { "Federated":
    "arn:aws:iam::012345678901:oidc-provider/oidc-discovery.example.org" },
"Condition": { "StringEquals": {
    "oidc-discovery.example.org:aud": "mys3",
    "oidc-discovery.example.org:sub": "spiffe://example.org/ns/default/sa/default"
}}

Opposite rules for two tasks that look identical on a diagram. And note what the second one introduces: AWS and Entra fetch that JWKS over the public internet, so cross-Cloud auth now depends on an endpoint you operate, with DNS and a certificate. If it is unreachable, all three legs stop federating together. The managed metadata servers have no equivalent single point.

The SPIFFE Project Got There First

None of that is a niche objection, and the maintainers reached it before I did.

There is an RFC for serverless support, spiffe/spire#1843, proposing an agentless path where the function attests directly to the Server. It was opened in September 2020. It is still a proposal.

What it proposes to attest with closes the argument:

  • For Google Cloud Functions, validate the identity token from the Compute Metadata Server.
  • For AWS Lambda, sign a GetCallerIdentity query with SigV4 and let the Server replay it.

Those are the two primitives this framework already calls directly. The coordinator mints the metadata token itself, and running the coordinator on AWS instead already signs a GetCallerIdentity request and hands it to Google's STS. On serverless, SPIRE's own design is a wrapper around what the mesh does today.

The One Argument That Does Land

I want to give the strongest version of the other side, because there is one and it is not the one the articles lead with.

AWS already has the field these pieces keep asking for. SourceIdentity is set once, cannot be changed, survives role chaining, and appears on every action taken with the role. Session tags do the same for attributes. If you want to record which Agent relayed a call, AWS will store it.

Both are filled from claims inside the web identity token — not from a request parameter. The caller cannot set them. The identity provider has to. And the GCE metadata identity endpoint takes three query parameters, which is the whole surface:

GET /computeMetadata/v1/instance/service-accounts/default/identity
      ?audience=<your audience>
      &format=full
      &licenses=FALSE

The claim set is fixed. No parameter adds one. So two of the three Clouds would accept a delegation chain and none of the three legs can send one, because they all start at a minter with no way to say anything beyond an audience.

Run the Server yourself and the claim set is yours. That is a real gain and it does not shrink as the mesh gets smaller. It is also not what "adopt SPIFFE for workload identity" is selling — you already have workload identity. The gap is claims, which is narrower and has cheaper answers.

But You Could Make It Work

You could, and the design is worth writing out properly, because it is the obvious response to everything above and it is not silly.

Nobody says the SPIRE Agent has to run on the serverless runtime. Only the caller needs an identity, and there is one caller. So: run the Server on a VM or a small GKE cluster. Have the coordinator present its Cloud Run metadata token to the Server and get back a JWT-SVID carrying whatever claims you want. Publish the JWKS through the OIDC Discovery Provider, point the AWS and Entra trust policies at it, and you have one SPIFFE ID and full control of the claim set.

That works on a whiteboard. Here is what each part of it costs.

The SVID is asserted, not attested

SPIFFE's whole value is attestation — an identity bound to something observed about the workload. In this design the Server observes nothing. It receives a Google token and re-signs its claims under a new name.

So the SPIFFE ID means exactly what the Google token meant, no more, because that is the only evidence in the chain. You have not added attestation. You have added a signing hop, and a private key to look after. The resulting identity is strictly weaker than the one it wrapped: same evidence, extra key.

It creates a new secret zero, and it is the best one in the building

The CA signing key is now the most valuable secret you own. Anyone who takes it mints identities that AWS and Entra will accept for your roles, and the metadata server they are impersonating never gets consulted.

The stated goal of this whole exercise was no long-lived secrets anywhere in the mesh. Today there are none — Google holds the signing key, and if that key is compromised it is Google's problem and everyone's problem at once. Adopting SPIFFE to remove secret zero would introduce a new one, more valuable than any it removed, on infrastructure you patch yourself.

The GCP leg cannot use it anyway

Cloud Run's invoker check validates Google-signed ID tokens. It does not take an arbitrary external issuer, so a JWT-SVID is not a credential that leg can use.

You have two ways round that and neither is good. Skip that leg, and you are running SPIFFE for two of three Clouds while the third keeps using Google tokens — more mechanisms than you started with, not fewer. Or exchange the SVID back into a Google credential through Workload Identity Federation, which means minting a Google token, converting it to an SVID, then converting it back to a Google token. A round trip to arrive where you began.

The pinning does not collapse to one

The promised win was three places down to one. Count the places again after adopting it:

  • AWS — an IAM OIDC provider, plus a trust policy naming the SPIFFE ID
  • Entra — a federated credential naming the issuer and subject
  • GCP — a workload identity pool and provider, or the invoker binding
  • SPIRE — registration entries, which is a fourth registry that did not exist before

A trust domain unifies the format of the identity. It does not reduce the number of places that decide what the identity may do, because that decision belongs to each far end and cannot be delegated to your Server. Three mappings before, three mappings and a registry after.

And SPIFFE Federation is not the escape hatch

The usual reply at this point is that SPIFFE has federation built in, so let the trust domains federate and the problem goes away.

It does not, because of what federation is. The SPIFFE Federation specification defines an exchange of trust bundles between trust domains, each publishing an HTTPS bundle endpoint the other polls. No identities are delegated and no keys are shared — the domains simply learn to verify each other's SVIDs.

That requires the far side to be a SPIFFE trust domain publishing a SPIFFE bundle endpoint. AWS is not one. Neither is Azure, nor Google. There is nothing on the other end to federate with, so federation is available exactly when both parties already run SPIFFE — which is meaning A again.

The spec is also explicit that its scope stops at verifying identities issued elsewhere. It carries no authorization semantics across the boundary, which is the same limit the Clouds have and for the same reason.

It puts one endpoint you host in the path of all three legs

This is the one I would refuse on even if the others were solved.

AWS and Entra validate a JWT-SVID by fetching your JWKS over the public internet. So every cross-Cloud call in the mesh now depends on a discovery endpoint you run, on DNS you manage, behind a certificate you renew.

A multicloud mesh whose auth funnels through one self-hosted endpoint is not multicloud where it counts. Today the three legs fail independently — each depends on its own vendor's identity service, and no single outage takes all three. Add the discovery provider and you have three independent dependencies plus one shared one, sitting in front of all of them.

You would be introducing a common failure mode into the part of the system built specifically to avoid one. Multicloud is supposed to buy independence; this spends it.

None of these are objections to SPIFFE. They are objections to bolting a token exchange onto a substrate the design was not drawn for. Every one of the five costs you something the current arrangement provides for nothing.

Where SPIRE is the Right Call

Meaning A, and it is not a grudging concession — inside a boundary you control, SPIRE is doing something the Clouds do not do for you.

  • Your Agents run on Kubernetes. Nodes exist, the k8s node attestor works, and every objection above except the operational one disappears.
  • You have a lot of identities. Somewhere past a dozen across three Clouds, verifying pinnings by hand stops working and one trust domain starts paying for itself.
  • You need workload-to-workload mTLS. X.509-SVIDs are a genuinely better answer than anything you would assemble from three Clouds' primitives.

None of those describe a serverless Agent mesh calling managed runtimes on three vendors.

This Ground Has Been Covered

I went looking for prior work expecting thin pickings, on the assumption that Agent identity is too new to have a literature. That was wrong, and the reason it looked empty is that most of the work is filed under workload identity and microservices rather than under Agents.

Two IETF efforts are directly on this problem.

WIMSE — workload identity in multi-system environments

The WIMSE working group is chartered for exactly this: least-privilege access control for workloads deployed across multiple platforms, public and private. Its output includes an architecture draft, a Workload Identifier, Workload Credentials, and a Workload Proof Token that binds a workload's authentication to a specific HTTP request.

The one worth reading before adopting anything is Workload Identity Practices (Schwenkschuster and Rosomakho, draft 06, August 2026), which surveys how workloads actually get credentials today. It does not treat SPIFFE as the only legitimate answer. It documents the Instance Metadata Endpoint as an established industry pattern in its own right:

"The biggest cloud providers have established the pattern of an 'Instance Metadata Endpoint'. Aside from allowing workloads to retrieve metadata about themselves, it also allows them to receive identity."

And for the cross-Cloud case: "the workload first needs to federate to the Secure Token Service (STS) of the respective cloud, which is effectively an Identity Provider."

That is a description of what this mesh does, in a standards-track document, listed alongside SPIFFE rather than as the thing SPIFFE replaces. It also carries a requirement worth checking your own implementation against: a credential for internal platform access should not be reused to federate to an external STS, because doing so conflates trust and audience boundaries. This mesh mints a separate token per destination — the service URL for the GCP leg, sts.amazonaws.com for AWS, api://AzureADTokenExchange for Entra — so it complies, but only because the audiences were chosen deliberately.

Transaction Tokens — the call chain, as a separate concern

Transaction Tokens (draft 08, March 2026, OAuth WG) exist to carry user identity, workload identity and authorization context along a call chain inside a trust domain. They are short-lived signed JWTs issued by a Transaction Token Service, which implements a profile of the OAuth 2.0 Token Exchange endpoint, and they are cryptographically protected so downstream workloads cannot alter the context or invent a call that no transaction started.

This is the microservices industry having already learned the lesson: passing the caller's access token down the chain does not work, and the fix is a separate token for the chain, not a better credential for the workload.

There is an agent-specific extension, Transaction Tokens for Agents (Ashay Raut, Amazon), which uses sub for the principal and act for the Agent acting, with sub set to the Agent itself when it is operating autonomously. Be honest about its standing: that draft has expired and been replaced by an individual submission. The work is under way, not settled.

And there is a literature

  • Authorization Propagation in Multi-Agent AI Systems (Krti Tallam, May 2026) formalises the problem as a workflow-level property, names three sub-problems — transitive delegation, aggregation inference, temporal validity — and derives seven structural requirements. Its verdict on the state of the art is the useful part: recent work "demonstrates that the field is converging on the problem, but not yet on a complete architecture." It also reports that ordinary system behaviour, not only attacks, already produces these failures in a production platform.
  • OpenID Connect for Agents (OIDC-A) 1.0 proposes an OIDC extension with agent identity, delegation-chain representation and attestation evidence compatible with IETF RATS and Entity Attestation Tokens. It is a proposal by an individual author, not an adopted OpenID specification, and should be read as one.

The picture that emerges is not that nobody has thought about this. It is that the standards bodies have split the problem in two — a credential for the workload, and a separate token for the chain — while the Agent-identity articles keep proposing a single mechanism for both.

What a Valid Alternative Looks Like

The mistake running through the Agent-identity writing is trying to solve a call-chain problem with a workload-identity tool. Those are two axes, the standards bodies have already separated them, and an architecture that separates them is buildable today on every runtime in this mesh.

Four layers. Each one has a specification behind it, and none of them requires a node.

Layer 1 — who is calling

Platform workload identity, per destination

Keep the metadata mint. It is attested by the only party positioned to attest anything on serverless, it costs nothing to run, and the WIMSE practices draft documents it as an established pattern rather than a shortcut.

The rule to enforce is audience separation: one token per destination, never a platform-internal credential reused against an external STS. That is what stops a token minted for one boundary being replayed at another, and it is the requirement most homegrown implementations miss.

Layer 2 — on whose behalf, and through whom

A transaction token for the call chain

This is the layer the mesh does not have and the one every article is really asking for. A Transaction Token Service sits at the edge, takes the incoming request plus whatever authenticated the requester, and issues a short-lived signed JWT carrying sub for the principal and act for the Agent acting. Each Agent in the chain presents it, and requests a new one to call the next hop, so the chain accumulates rather than being asserted.

Two properties make this the right shape. The token is immutable in transit, so a downstream Agent cannot widen the context it was handed or fabricate a transaction that never started. And it is separate from the credential, so it is unaffected by the fact that three Clouds each dictate their own credential format.

The Txn-Token Service is a service you run, which is a real cost — but note the difference from a SPIRE Server. It is not in the credential path. If it is down, you stop starting new work; you do not lose the ability to authenticate, and no Cloud is fetching keys from you to validate a login.

Layer 3 — carried by the protocol

A2A message metadata, not the credential

The transaction token travels in the A2A message. The extension mechanism added in v1.0.1 is the sanctioned place, and the Secure Passport extension already defines a CallerContext attached beside the task with a client identifier, state and a signature.

Use the extension as the envelope and a transaction token as the payload, and the two weaknesses cancel: Secure Passport supplies a standard carrier that every A2A implementation can be taught to read, and the transaction token supplies the delegation semantics and signing model that Secure Passport deliberately leaves open.

Declare it on the Agent Card too. A2A carries securitySchemes in OpenAPI 3 shape plus a security block that maps scopes to individual skills, so a client can learn what an Agent requires by reading rather than by failing. Most deployments, this one included, declare far less than the spec allows.

Layer 4 — narrowing, per hop

Attenuate the credential at the boundary that supports it

Where a Cloud lets you narrow a credential below what the role permits, do it per call rather than per deployment. On the AWS leg an inline session policy on AssumeRoleWithWebIdentity intersects with the role and can never widen it, so the session can be scoped to the single action a given hop needs.

Measured on this mesh: narrow the session to card discovery and the invocation is refused; narrow it to invocation and the card fetch is refused first. Both refusals name the session policy as the layer that said no. This is the one rule of the three that a deployment can demonstrate rather than assert.

Why this beats bolting on SPIRE

Layer 1 is free and already attested. Layer 2 is a service you run, but outside the credential path, so its failure mode is "no new work" rather than "no authentication anywhere". Layer 3 is protocol machinery that already exists. Layer 4 is a request parameter.

Against that, the SPIRE design puts a service you run and a public discovery endpoint inside the credential path for all three legs, to obtain claim control that layer 2 provides without touching credentials at all.

The honest caveat: nobody has finished this. Transaction Tokens are at draft 08, the agent extension has expired and been replaced by an individual submission, OIDC-A is one author's proposal, and the paper that frames the problem best concludes the field is "converging on the problem, but not yet on a complete architecture."

So this is a direction with standards behind it rather than a product you can adopt. What makes it the right direction anyway is that it is decomposed correctly — and layers 1, 3 and 4 are all available now, whatever happens to layer 2.

The two-afternoon version

If none of that is happening this quarter, the useful subset is small.

Put a requester field on the run record. Until a run carries who asked for it, the audit trail names the coordinator as the actor for everything — the original complaint in every one of these articles, and fixable in an afternoon without a single new component.

Then use RoleSessionName. It is required on every AssumeRoleWithWebIdentity call, caller's choice, two to sixty-four characters, and it lands in the assumed-role ARN and in CloudTrail. It is the only caller-supplied identity string in this mesh that reaches a Cloud provider's audit log, and it is currently a constant. A run correlator there makes a CloudTrail entry traceable to a specific run, for one extra STS call per run.

Two I would not start with

Running your own OIDC issuer gets you claim control and makes you an identity provider — key custody, rotation and availability become yours, and you inherit the public-endpoint failure mode without the attestation that justified it.

And a single egress broker holding all three federations builds the target you least want. Reviewing this project for these articles turned up its own coordinator open to the internet on a public invoker binding, with three sets of federated credentials behind it. A broker makes that surface the architecture rather than the accident.

Summary

Three Agents are deployed across GCP, AWS and Azure with a coordinator on Cloud Run, federating three ways with no stored secrets and eight controls confirming it. The protocol never needed a change. The auth strategy took the effort and is what would break first.

SPIFFE and SPIRE are the default recommendation for that strategy and they are solving the other multicloud problem — identity for workloads inside a boundary you control. An Agent mesh is the case where you control one end and three vendors dictate the rest, and no identity format changes that. SPIRE removes none of the federations, adds a Server and a public endpoint, and needs a node to attest that serverless runtimes do not have.

The reason it removes none of them is worth carrying away on its own. A Cloud identity has no meaning outside its Cloud. AWS checks Google's signature and then applies a rule you wrote about a number it has never seen before; authentication crosses the boundary and authorization never does. Every far end has to decide locally what a foreign identity may do, so the mapping exists once per boundary no matter who issues the token. Change the issuer and you have changed the signature, not the arithmetic.

What is actually missing is narrower than the articles suggest, and the standards bodies have already split it correctly. A credential identifies the workload, and the Clouds hand you an attested one for free. A separate token carries the call chain — who asked, and which Agent is acting — because that context cannot survive inside a credential three vendors each define differently. WIMSE is standardising the first half and OAuth Transaction Tokens the second, and A2A's extension mechanism is where the second one travels.

None of that is finished. Transaction Tokens are at draft 08, the Agent extension has expired into an individual submission, and the best paper on the problem concludes the field is converging on it but not yet on an architecture. What can be said is that the decomposition is right, three of the four layers are available today, and the one that is not does not sit in the credential path — which is exactly the property the SPIRE design gives up.
