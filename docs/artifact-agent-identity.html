Same Mesh, a Different Question

The earlier articles in this series put agents on GCP, AWS and Azure and timed the A2A calls between them. Speed was the variable. Identity was whatever it took to make the call connect.

That is the wrong way round for anything going into production, and there is now a good deal of writing that says so. The best-argued version I have read is Jitendra Gupta's piece on agent identity, which makes a claim worth taking seriously: enterprise agents are running on generic service accounts, the way applications did fifteen years ago, and that single flat identity destroys the three facts you need afterwards — who asked, which agent acted, and under whose authority.

It is a design argument. It cites no deployment. I happen to have a three-cloud mesh already running, so this article puts the argument on it and reports what the clouds actually do.

What is Agent Identity Supposed to Solve?

The proposal reduces to three rules. Stated fairly, before I go anywhere near them:

  • Rule 1 — no stored secrets. An agent should not bootstrap from a hardcoded key. It should attest to the platform and be issued a short-lived credential.
  • Rule 2 — never lose the delegation chain. The token should carry who initiated the work and which agents relayed it, nested, all the way down.
  • Rule 3 — permissions must shrink. Every handoff narrows the grant, so the final permission is an intersection rather than a union.

The recommended stack is SPIFFE and SPIRE for workload identity, OAuth 2.0 token exchange for delegated authorization, DPoP to bind tokens to a workload, and scope attenuation at each hop.

The Test Bed

Three research agents, one per cloud, plus a coordinator that fans a brief out to all three and scores the drafts. The coordinator runs on Cloud Run for one reason: it is the runtime I have confirmed will mint a workload OIDC token with an arbitrary audience, which is what makes every outbound leg a candidate for keyless federation.

Each leg starts at the same place — the metadata server — and then diverges:

GCP → GCP Google ID token, audience pinned to the service URL An in-cloud hop, and labelled as one. It does not count toward the interop claim.
GCP → AWS Token to STS AssumeRoleWithWebIdentity, then SigV4 AWS federates with accounts.google.com natively. Trust is pinned to the service account's numeric ID, never its email.
GCP → Azure Token to an Entra Federated Identity Credential Presented as a client assertion in place of a client secret.

Every leg has a positive control and a negative control: run it as deployed, then run it with the credential removed and confirm it is refused. There is also a wrong-audience probe on the GCP leg, which is the one that separates this identity is checked from some token is checked. All eight hold on the current build.

Rule 1 — No Stored Secrets Anywhere

This one the mesh already satisfies, and the interesting part is that it satisfies it without SPIFFE.

SPIRE exists to give you an attested identity document where the platform gives you none. Cloud Run gives you one. The metadata server issues a short-lived, audience-scoped JWT whose subject the runtime vouches for and the workload cannot forge, which is the same class of object as a JWT-SVID. The trust conditions on the AWS and Azure sides are written against that subject's immutable numeric ID.

The OAuth half is not an analogy either. It is literally OAuth: the Azure leg presents a JWT bearer client assertion, and the reverse direction — running the coordinator on AWS instead — uses the RFC 8693 token-exchange grant against Google's STS.

So the "missing layer" is the seam between the two. One credential adapter, one interface, three implementations behind it. Adding SPIRE here would insert an issuer nobody attests, and every callee would still have to trust its keys in addition to the three federations that already work. At three peers that is a component for nothing. At thirty, when the same identity is re-pinned in thirty places and free to drift, the trade flips.

Rule 3 — Permissions Must Shrink

Taking the third rule before the second, because it is the one that measures cleanly.

STS is the only one of the three exchanges that accepts a caller-supplied policy. AssumeRoleWithWebIdentity takes an optional inline session policy of up to 2,048 characters, and the resulting session gets the intersection of the role's policy and that one. There is no way to write a session policy that grants something the role lacks, which is exactly what makes it worth having: the role is provisioned once and outlives every run, while the session policy is chosen per process and costs nothing to make smaller.

The mesh's AWS role is already scoped to two actions on one runtime ARN. So the test is whether a session can narrow it further, and whether the two actions come apart.

The pair is the result. Neither action stands in for the other in either direction, under a session the role would otherwise have permitted. Attenuation works across a federation boundary, and discovery is authorized separately from invocation — a point this project first hit a fortnight earlier, now holding under a second and narrower grant.

Two details worth carrying away. AWS names the session policy as the layer that refused, which distinguishes an attenuation refusal from a role refusal without any guessing. And the invoke-only run is what proves the card fetch genuinely succeeded in the card-only run rather than being skipped: when discovery is the narrowed action, the leg never reaches the invocation at all.

This is the one rule of the three that a deployed mesh can demonstrate rather than assert. It is also worth being clear about why it is demonstrable: AWS built session policies for this years ago. Nothing agent-specific was added.

Rule 2 — The Delegation Chain

Here the proposal and the hardware part company, and the reason is more interesting than a straight no.

AWS has two fields built for precisely this job. SourceIdentity is immutable once set, persists across role chaining, and is present on every action taken with the role — functionally the "who initiated this" field, shipped long before anyone framed it as an agent problem. Session tags do the attribute half and can be read back in IAM conditions.

Both are populated from claims inside the web identity token, never from a request parameter. The caller cannot set them. The identity provider must.

And the identity provider cannot. The GCE metadata identity endpoint accepts three query parameters — audience, format and licenses — and mints a fixed claim set: issuer, issued-at, expiry, audience, subject, authorized party, email and verification flag, plus a Compute Engine block under format=full. There is no parameter that adds a claim, and no claim in the set that carries an actor.

The constraint is the minter, not the consumer. Two of the three clouds would happily accept a delegation chain. None of the three legs can carry one, because they all start at a metadata server that offers no way to say anything beyond an audience.

That generalizes past this mesh. Any agent taking its identity from a cloud metadata server inherits that cloud's claim set and cannot add to it. Delegation therefore has to travel beside the credential — in the A2A message — and be verified by each agent in turn. That is a materially different design from the one the proposal draws.

One exception I have not exercised: Bedrock AgentCore accepts a JWT from an issuer you control, so that leg could carry a nested chain if it stopped using SigV4. One of three.

The 64 Characters Nobody is Using

There is exactly one caller-supplied identity string in this mesh that reaches a cloud provider's audit log, and it is easy to miss because it looks like a formality.

RoleSessionName is required on every AssumeRoleWithWebIdentity call. Two to sixty-four characters, word characters plus =,.@-. It lands in the assumed-role ARN and in CloudTrail, and it is chosen entirely by the caller.

This mesh sets it to a constant. That is defensible — a stale session name silently mislabels every call you make in somebody else's audit log — but it means the one available field carries no per-run information. Putting a run correlator there would make a CloudTrail entry traceable to a specific run. The cost is one STS call per run instead of one per process, because the session name is fixed when the credential is minted and the credential is cached.

I have not made that trade. I am writing it down so the next person does not have to rediscover that the field is there.

Where the Proposal is Ahead

It names the human, and this mesh has none.

The whole argument turns on on behalf of whom. The mesh has no answer, because it has never been asked the question: every identity in it is a machine, the run record carries a run ID and no requester, and the chain is one hop deep. That is not a gap in the implementation. It is a gap in the problem I chose, and the proposal is right that it is the half that matters once a person is in the loop.

The third rule landed on this project too. A coordinator holding federated credentials for three clouds is the softest target in any mesh, and it is exactly the surface that gets opened to the internet to try something once. Reviewing it for this article is what turned that up, and closing it took a revoked binding and a redeployed flag. The controls found it. They found it four days after the fact, which is an argument for running them on a schedule rather than before a write-up.

The two are not really competing. One is a design for the human-to-agent boundary with nothing deployed behind it. The other is a measured implementation of the agent-to-agent boundary with no human in it. Each is strongest where the other is empty.

Where they genuinely conflict is the mechanism, and there the hardware settles it: the chain does not fit inside the credential.

Summary

Three research agents were deployed across GCP, AWS and Azure, coordinated from Cloud Run, with every outbound leg authenticated by a federated credential and no long-lived secret anywhere in the mesh.

Against those three legs, one of the proposal's rules was demonstrated by measurement — permissions narrow across a federation boundary, and discovery and invocation narrow independently. One was already satisfied, by the platform rather than by the recommended stack. And one turned out not to be buildable the way it is drawn, because the field that would carry it is filled by the identity provider and the identity provider offers no way to fill it.

The next piece of work is the cheap half of that third result, and it needs none of the machinery: record who asked. Until a run carries a requester, the audit trail names the coordinator as the actor for everything — which is the original complaint, correctly aimed.
