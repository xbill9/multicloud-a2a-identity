Cross-Cloud A2A

Auth is the Limiting Factor in Cross-Cloud A2A

The protocol works. Three rounds of benchmarks across GCP, AWS and Azure never turned up a protocol problem. What decides whether a multi-Cloud Agent mesh ships is the auth strategy behind it — so this article works out whether SPIFFE and SPIRE are that strategy, and what the alternatives are if they are not.

The Protocol is the Easy Part

A2A does what it says. Cards resolve, tasks come back, and the client libraries in three different languages talk to each other without special cases. Across the benchmark series the timings tracked the remote model and runtime — they never tracked anything in the wire format. There is no protocol work left to do to run Agents on three Clouds.

Auth is where it stops, and it stops hard. Every cross-Cloud call needs a credential the far side will accept, and the far side is a different vendor with a different notion of what an acceptable credential is. A2A is deliberately silent here: the spec has the client discover the scheme from the Agent Card and obtain the credential out of band. Out of band is doing a lot of work in that sentence. It is the entire integration.

So the interesting question for a multi-Cloud mesh is not which protocol to use. It is which auth strategy to build under it. The recommendation you will see most often is SPIFFE and SPIRE — Jitendra Gupta's article on Agent identity is the clearest version of the case. It is usually made in the abstract. I have the mesh deployed, so this works out what adopting it would actually cost, and what else is on the table.

What are SPIFFE and SPIRE?

SPIFFE is the specification. Every workload gets an ID shaped like a URI — spiffe://example.org/coordinator — carried in one of two credential formats: an X.509-SVID for mTLS, or a JWT-SVID for anything that wants a bearer token.

SPIRE is the implementation, and it has three parts:

  • SPIRE Server. One per trust domain. Signs SVIDs, holds registration entries, needs a datastore and an HA plan.
  • SPIRE Agent. Runs on every node beside the workloads. It attests the node to the Server, then attests each local workload and hands it an SVID over a Unix socket.
  • OIDC Discovery Provider. Publishes the JWKS so an outside Cloud can validate a JWT-SVID. This is what makes cross-Cloud federation possible at all.

Keep the middle one in mind. SPIRE's trust model starts with a node it can attest.

What Does the Framework Already Do?

The coordinator runs on Cloud Run and calls three Agents. Every leg starts at the same place — the metadata server issues a short-lived OIDC token with whatever audience you ask for — then diverges by Cloud:

GCP → GCP Google ID token, audience pinned to the service URL
GCP → AWS Token to STS AssumeRoleWithWebIdentity, then SigV4
GCP → Azure Token to an Entra Federated Identity Credential

No stored secrets on any of them. Each leg has a positive control and a negative control — run it as deployed, then run it with the credential removed and confirm it is refused. Eight probes, all holding on the current build.

That is already the thing SPIFFE exists to provide. The metadata server issues a short-lived, audience-scoped token the platform vouches for and the workload cannot forge. Same class of object as a JWT-SVID, and the trust conditions on AWS and Azure are written against its subject.

So Why Would I Need SPIRE? Can't I Just Use the Metadata Server?

For three legs, mostly yes. Two real arguments against, and only one of them is about scale.

The identity is pinned in three places

The coordinator has one identity — a service account with a numeric ID. That number is written down three times in three vendors' formats: a condition in an AWS trust policy, the subject on an Entra federated credential, an IAM binding on Cloud Run.

Nothing keeps them in sync. The Azure deploy script has a verify step that reads the federated credential back and compares it against the service account, and that step exists because the two can drift. At three pinnings you can check by hand. At thirty you cannot, and that is the case SPIRE is built for.

You do not control the claims

This one is not about scale, and it is the argument I take seriously.

AWS already has the field these Agent-identity articles keep asking for. SourceIdentity is set once, cannot be changed, survives role chaining, and shows up on every action taken with the role. Session tags do the same for attributes. If you want to record which Agent relayed a call, AWS will store it for you.

Both are filled from claims inside the web identity token. Not from a request parameter — the caller cannot set them. The identity provider has to.

On this framework the identity provider will not. The GCE metadata identity endpoint takes three query parameters and that is the whole surface:

GET /computeMetadata/v1/instance/service-accounts/default/identity
      ?audience=<your audience>
      &format=full
      &licenses=FALSE

The claim set that comes back is fixed: issuer, issued-at, expiry, audience, subject, authorized party, email, verified flag, and a Compute Engine block if you ask for format=full. No parameter adds a claim.

Two of the three Clouds would accept a delegation chain. None of the three legs can send one, because they all start at a metadata server with no way to say anything beyond an audience.

Run the Server yourself and the claim set is yours. That is the strongest technical argument for SPIRE here, and it is worth separating from the scale one, because it does not go away as the mesh gets smaller.

Where Does the SPIRE Agent Actually Run?

Here the idea meets the framework, and it is an architectural mismatch rather than a matter of effort.

The three runtimes are Cloud Run, Bedrock AgentCore and Azure Container Apps. None of them gives you a node. There is no host to run a daemon on and no socket to share, and the containers come and go per request.

The SPIFFE project knows. There is an RFC for serverless support — spiffe/spire#1843 — proposing an agentless path where the function attests straight to the Server. It was opened in September 2020 and it is still a proposal.

What it proposes to attest with is the part worth reading:

  • For Google Cloud Functions, validate the identity token from the Compute Metadata Server.
  • For AWS Lambda, sign a GetCallerIdentity query with SigV4 and let the Server replay it.

Those are the two primitives this framework already calls directly. The coordinator mints the metadata token itself, and running the coordinator on AWS instead already signs a GetCallerIdentity request and hands it to Google's STS as a subject token. On serverless, SPIRE's own plan is to wrap what the mesh does today.

The Trust Policy is Not the Same Shape

One more thing before costing it out. Federating to AWS from SPIRE is a different configuration from federating from Google, and it is the kind of difference that produces a confusing failure rather than a clear one.

Google is a native AWS identity provider. You do not create an IAM OIDC provider for it — if you do, federation stops working:

"Principal": { "Federated": "accounts.google.com" },
"Condition": { "StringEquals": {
    "accounts.google.com:oaud": "sts.amazonaws.com",
    "accounts.google.com:sub":  "<service account numeric ID>"
}}

SPIRE is not native, so the IAM OIDC provider is required, and conditions key on your own discovery domain:

"Principal": { "Federated":
    "arn:aws:iam::012345678901:oidc-provider/oidc-discovery.example.org" },
"Condition": { "StringEquals": {
    "oidc-discovery.example.org:aud": "mys3",
    "oidc-discovery.example.org:sub": "spiffe://example.org/ns/default/sa/default"
}}

Opposite rules for two tasks that look identical on a diagram. Note also that the discovery domain is a real deliverable — AWS and Entra fetch the JWKS over the public internet, so it needs DNS, a certificate and uptime. If it goes down, every leg stops federating at once.

Read the fourth row twice. SPIRE does not replace the federations. Every Agent here consumes external OIDC and carries on doing so — AWS still needs a trust policy, Entra still needs a credential, Cloud Run still needs an invoker binding. You add a Server, an Agent, a public endpoint and a certificate, and keep all three. What you remove is one number written down three times.

So Does it Make Sense?

Not for this framework as it stands. Three reasons, in order:

  1. There is nowhere to put the Agent. All three runtimes are serverless and the agentless path has been a proposal since 2020.
  2. The gain is deduplicating three pinnings. Three is a number a script can verify, which the deploy already does.
  3. You swap a managed minter with no operational cost for one you run, and add a public endpoint whose outage takes down all three legs together.

Put the Agents on EKS, GKE or AKS and the first reason evaporates — you have nodes, the Kubernetes node attestor works, and the argument becomes a normal build-versus-buy. That is the honest boundary of this verdict. It is about serverless, not about SPIFFE.

If Not SPIRE, Then What?

This is the part the identity articles tend to skip. Here are the six options I looked at, ordered by how well they fit a serverless multi-Cloud mesh. Worst fit last.

1. Native workload identity federation

What the mesh runs now. The platform mints an attested token, each Cloud federates it in its own way. Nothing to install, nothing to operate, and the minter is somebody else's uptime problem.

You give up control of the claims, and the identity gets pinned once per Cloud. For a handful of Agents this is the right default, and it is worth choosing deliberately rather than ending up on it.

Fits now · no delegation chain

2. Carry delegation in the A2A message

If the constraint is that the credential cannot hold the chain, stop trying to put it there. A2A added an extension mechanism in v1.0.1, and one of the official extensions is Secure Passport — a CallerContext object attached as metadata alongside the task, carrying a client identifier, arbitrary state and a signature.

That is the right seam for this problem. The credential proves the calling service; the passport says who the work is for and who relayed it, and each Agent verifies it in turn. It works on every runtime because it never touches the credential path.

Two honest caveats. Secure Passport is aimed at context sharing rather than a formal delegation model, so you are defining the semantics yourself. And a signature needs a key and a trust story of its own — which is a smaller problem than SPIRE, but it is not nothing.

Fits now · closest to the actual gap

3. Use the Agent Card properly

A2A already carries securitySchemes on the Agent Card, in the same shape as OpenAPI 3, plus a security block that can map scopes to individual skills. Most deployments — this one included — declare far less than the spec allows.

It will not mint you anything. What it gives you is the scheme stated in a machine-readable place, per skill, so a client finds out what an Agent requires by reading rather than by trying. Cheapest item on this list.

Fits now · declarative only

4. Managed SPIFFE instead of self-hosted SPIRE

Teleport Workload Identity issues the same SPIFFE IDs and SVIDs, serves the same Workload API, and federates with SPIRE trust domains, so standard SDKs work unmodified. It supports a wider set of attestation methods than SPIRE — including CI systems and AWS Roles Anywhere — and takes the Server operations off you.

It does not solve the part that actually blocks this framework. You still need its agent running somewhere alongside the workload, and serverless still has nowhere to put it. Worth a look the moment the Agents land on Kubernetes.

Better on Kubernetes · same serverless gap

5. Run your own OIDC issuer

The tempting shortcut. Take the platform-attested metadata token, exchange it for a JWT you sign with whatever claims you want, publish a JWKS, and point the AWS and Entra trust policies at that. It is SPIRE's discovery provider without SPIRE, and it gets you the claims control that motivated the whole exercise.

It also makes you an identity provider. Key rotation, signing key custody and availability all become yours, and you inherit the public-endpoint failure mode — if the JWKS is unreachable, every leg stops — without any of the attestation machinery that justified it. I would want a much stronger reason than claims to take this on.

Do not start here

6. One egress broker in front of everything

Put a single authenticated proxy in front of all cross-Cloud calls. It holds the three federations, and Agents authenticate to it locally. Attractive because the credential work happens once.

It also builds exactly the target you least want: one service holding credentials for every Cloud, with a wide front door. Reviewing this project for these articles turned up its coordinator open to the internet on a public invoker binding — a surface with three sets of federated credentials behind it. Closing it took a revoked binding and a redeployed flag. A broker makes that surface the architecture rather than the accident.

Concentrates the risk

What I Would Do on This Framework

Options one, two and three, in that order, and none of them needs a new identity system.

Keep native federation for the credential. Add the delegation context to the A2A message where the protocol already has a slot for it. Fill in the Agent Card so the scheme is declared rather than discovered by failure.

Then two small things that are worth more than they look. The run record needs a requester field — until a run carries who asked for it, the audit trail names the coordinator as the actor for everything, which is the original complaint in all these articles and is fixable in an afternoon. And RoleSessionName on AssumeRoleWithWebIdentity is caller's choice, two to sixty-four characters, and lands in CloudTrail. It is the only caller-supplied identity string in this mesh that reaches a Cloud provider's audit log, and it is currently a constant. A run correlator there makes a CloudTrail entry traceable to a specific run, for one extra STS call per run.

Summary

A2A is not the constraint on multi-Cloud Agents. Three Agents are deployed across GCP, AWS and Azure with a coordinator on Cloud Run, federating three ways with no stored secrets, and the protocol never needed a change to make that work. The auth strategy is what took the effort and what would break first.

SPIFFE and SPIRE are the usual recommendation and they do not currently fit this shape of deployment, because SPIRE needs a node to attest and serverless runtimes do not have one. That is a statement about serverless rather than about SPIFFE — on Kubernetes the calculation is completely different.

The alternatives are better than the silence around them suggests. Native federation already covers the credential. The A2A extension mechanism already has a place to carry the delegation context that the Cloud minters refuse to carry. Between those two, most of what the Agent-identity articles are asking for is available today without installing anything.
