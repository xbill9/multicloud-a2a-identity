Cross-Cloud A2A

Why SPIRE Doesn't Fit Multicloud Agents

A2A is not what limits a multi-Cloud Agent mesh. Auth is. The standard advice is to adopt SPIFFE and SPIRE, and on a deployed three-Cloud mesh that advice answers a different question than the one being asked.

The Protocol is the Easy Part

A2A does what it says. Cards resolve, tasks come back, and client libraries in three languages talk to each other without special cases. Across the benchmark series the timings tracked the remote model and runtime, never anything in the wire format. There is no protocol work left to do to run Agents on three Clouds.

Auth is where it stops. Every cross-Cloud call needs a credential the far side will accept, and the far side is a different vendor with a different notion of what acceptable means. A2A leaves this alone on purpose: the client reads the scheme off the Agent Card and gets the credential out of band. Out of band is the entire integration.

Ask what to do about it and you get pointed at SPIFFE and SPIRE. Jitendra Gupta's article on Agent identity is a well-argued version, and the recommendation is common enough now to be the default answer.

It is the wrong answer for this problem, and the reason comes down to one word.

Multicloud Means Two Different Things

The word does double duty, and the two meanings have nothing in common except the adjective.

Meaning A — what SPIRE is for

My workloads, spread across Clouds

You own the compute. Clusters on EKS, GKE and AKS, one organisation, one administrative boundary drawn around all of it.

  • You control the nodes
  • You choose the identity format
  • Both ends of every call are yours
  • One trust domain is a coherent idea
Meaning B — what an Agent mesh is

My Agent, calling other vendors' services

You own one end. The others are managed runtimes — Bedrock AgentCore, Azure Container Apps, Cloud Run — each with its own idea of a valid caller.

  • You control no nodes
  • Each far end dictates the format
  • Only the calling end is yours
  • Three trust domains, you administer one

SPIFFE was built for the first one. It gives identity to workloads inside a boundary you control and it is good at that. An Agent mesh is the second one, where the hard part is that the far end is not yours and never will be.

"SPIFFE is good for multicloud" is true of meaning A and gets repeated as though it were true of meaning B. The difficulty in meaning B is not that your workloads lack an identity. It is that three vendors each have their own rules about which identities they accept, and no identity format you adopt changes that.

What the Framework Runs

The coordinator runs on Cloud Run and calls three Agents. Every leg starts at the same place — the metadata server issues a short-lived OIDC token with whatever audience you ask for — then diverges by Cloud:

GCP → GCP Google ID token, audience pinned to the service URL
GCP → AWS Token to STS AssumeRoleWithWebIdentity, then SigV4
GCP → Azure Token to an Entra Federated Identity Credential

No stored secrets on any of them. Each leg has a positive control and a negative control — run it as deployed, then run it with the credential removed and confirm it is refused. Eight probes, all holding on the current build.

That is already what SPIFFE exists to provide. The metadata server issues a short-lived, audience-scoped JWT that the platform signs and the workload cannot forge or extract. A JWT-SVID in everything but the namespace, and the attestation behind it is stronger than anything you can install, because the attester is the runtime.

What a Cloud Identity Means Somewhere Else

Less than the diagrams imply, and this is the point everything else follows from.

When the coordinator presents a Google-signed token to STS, AWS does two things. It fetches Google's public keys from a well-known OIDC discovery endpoint and checks the signature. Then it applies the conditions you wrote into the role's trust policy — this audience, this subject.

That is the whole mechanism. AWS learns that a token was signed by whoever holds a key Google published, and that the token says sub is some number. It has never heard of your service account, your project or your Agent.

Authentication crosses the boundary. Authorization never does. The number in that token means what your trust policy says it means and nothing else. Delete the condition and the same valid token authorizes nothing.

There is no such thing as a cross-Cloud identity. There is a locally defined mapping, at each far end, from a foreign signature to a local principal. Three far ends, three mappings.

So writing the identity down three times is not a symptom of doing federation without SPIFFE. It is what a trust boundary is. Each side decides for itself what a foreign identity may do, because nobody else can decide it for them.

SPIRE changes whose signature is on the token. AWS still has to be told that spiffe://example.org/coordinator may assume a role, Entra still needs the same thing in its own format, and both mappings still live on their side of the wall. One issuer, still three mappings.

And what it means on Cloud Run

The same question turned inward is more uncomfortable.

That identity belongs to the service account, which is attached to the service. Not to a revision, not to an instance, not to a request. The token proves one thing: something running as this service account asked for it.

It does not distinguish one revision from the next, so a rollback or a bad image carries the identity you reviewed. It does not distinguish concurrent requests. And it does not distinguish callers at all — anything that gets code running in that container gets the full weight of it.

Reviewing this project for these articles turned up its coordinator open to the internet on a public invoker binding. While that was true, an anonymous request arrived and was served by a container holding federated credentials for three Clouds. The identity behaved correctly throughout. It was never designed to answer the question that mattered.

There is also no fixed node underneath any of it. A Cloud Run instance is created for a burst of traffic and destroyed, the service scales to zero between runs, and the next request may be served by something that did not exist a second earlier.

The substrate pulls two ways at once. The identity is too coarse — one service account across every revision and request. The compute is too fluid — no durable node to attest. SPIRE needs a stable node it can vouch for and an agent living on it long enough to vouch for the workloads above. Serverless offers neither half.

On a substrate with no fixed node, the platform is the only party that can attest anything. It is the only one that knows which image is running, in which revision, under which service account, at the instant the token is minted.

Three Clouds, Three Vocabularies

If every Cloud defines its own Agent identity, the obvious question is how any of it works across Clouds at all. The answer is that it works one ordered pair at a time, and it is worth going through properly, because the shape of the problem is not what the vendor diagrams suggest.

Start with what each Cloud lets a workload present as proof of who it is.

Google An OIDC JWT from the metadata server, with a caller-chosen audience
AWS A SigV4-signed GetCallerIdentity request — not a token at all
Azure An OIDC JWT from Entra, for a resource Entra recognises

Two of those are JWTs and one is a signed HTTP request. That difference is not cosmetic, and it decides which pairs can work.

Now what each Cloud accepts. Google's Workload Identity Federation is the most permissive: it takes a JWT from any OIDC issuer with a discovery document, and it also takes the AWS-shaped subject token, which it replays against AWS STS to learn who signed it. AWS takes JWTs from an OIDC issuer, natively for accounts.google.com and via an explicit IAM OIDC provider for anything else. Entra takes JWTs from an issuer publishing OIDC discovery, and nothing else.

The six edges

Three Clouds means six directed cross-Cloud edges, and each is decided independently by what the caller can present and what the callee will accept.

Directed edges between the three Clouds
EdgeMechanismKeylessStatus here
GCP → AWS Metadata JWT to STS AssumeRoleWithWebIdentity Yes Deployed
GCP → Azure Metadata JWT to an Entra federated credential Yes Deployed
AWS → GCP Signed GetCallerIdentity to Google STS, then impersonation Yes Implemented
AWS → Azure Client secret No Implemented
Azure → GCP Entra JWT to Google workload identity federation Yes Not built
Azure → AWS Entra JWT to an IAM OIDC provider for the Entra issuer Yes Not built

Six edges, five mechanisms, no two configured the same way. The first four are in this repository. The last two follow from the same rules and have not been deployed here.

The edge that does not close

AWS to Azure is the one that pays for the whole argument.

Google's federation accepts the AWS-shaped subject token, so AWS to GCP is keyless without AWS ever minting a JWT. Entra has no equivalent. Its federated credential wants a JWT assertion from an issuer with OIDC discovery, and an ECS task role, a Lambda execution role or an AgentCore runtime role is not one. Outside EKS with IRSA, or Cognito, AWS has nothing of that shape to present.

So that leg falls back to a stored client secret, and the mesh stops being secretless on exactly one of six edges. Not because anyone implemented it lazily — because the caller's native assertion is a signed request and the callee only reads JWTs from discoverable issuers. The two ends have no overlapping vocabulary.

This is what "different standards" means in practice. Not competing formats for the same idea, which you could convert between. Two ends that disagree about what an assertion is.

The arithmetic gets worse before it gets better

Three Clouds is six edges. Four is twelve. Each Cloud you add brings two edges for every Cloud already present, so the integration count grows as N², and every cell is somebody's bilateral decision to support somebody else.

That is why the vendor Agent identity products cannot be the general answer, however good each one is. AWS supporting Entra as an inbound provider fills one cell. Microsoft surfacing Bedrock and Vertex Agents in its registry fills a few more. Nobody is going to fill a quadratic matrix by negotiation, and the cells that stay empty are the ones where two vendors have no commercial reason to care about each other's workloads.

What would actually make it work

The fix is not a new identity format, and it is not a neutral issuer everyone adopts. It is narrower than either, and two of these three Clouds are close to it already.

Look again at where the asymmetry sits. Every Cloud can already mint something. The problem is on the accept side — whether an ingress will take a token from an issuer it does not own.

Will the ingress accept a foreign issuer?
RuntimeInbound authForeign issuer
Bedrock AgentCore SigV4, or a custom JWT authorizer with a discovery URL and allowed audiences Yes
Azure Container Apps Entra on the ingress Entra only
Cloud Run IAM invoker check against a Google-signed ID token Google only

AgentCore already does the thing that would fix this. Give it a discovery URL and a list of accepted audiences and it will validate a token from an issuer AWS has never heard of. That is the whole requirement, it is ordinary OIDC, and it needs no new specification.

If every Cloud's ingress accepted an OIDC discovery URL, an audience and a subject condition, the matrix would collapse from N² to N. Each Cloud publishes one issuer for its workloads. Each Cloud accepts any issuer, subject to conditions you write. Six edges become three mints and three accept-configurations, and adding a fourth Cloud costs one of each rather than six new integrations.

That is a change to three products, not a change to the industry. It also explains why the SPIRE proposal feels like it should work and does not pay off here: SPIRE is one issuer everyone trusts, which is the same collapse achieved by adding a party rather than by removing a restriction. The restriction is the cheaper thing to remove, and one vendor has already removed it.

There is More Prior Art Than It Looks Like

Search for Agent identity and you get opinion pieces. The engineering is there, but it is filed in three separate places, and none of them uses the words you would search for.

Tier one — the protocol work, which split the problem in two

The IETF WIMSE working group is chartered for least-privilege access control for workloads across multiple platforms, public and private. It has an architecture draft, a Workload Identifier, Workload Credentials, and a Workload Proof Token binding a workload's authentication to a specific HTTP request.

Read Workload Identity Practices before adopting anything — Schwenkschuster and Rosomakho, draft 06, August 2026. It surveys how workloads get credentials today, and it does not treat SPIFFE as the only legitimate answer:

"The biggest cloud providers have established the pattern of an 'Instance Metadata Endpoint'. Aside from allowing workloads to retrieve metadata about themselves, it also allows them to receive identity."

And for cross-Cloud: "the workload first needs to federate to the Secure Token Service (STS) of the respective cloud, which is effectively an Identity Provider."

That describes this mesh, in a standards-track document, listed beside SPIFFE rather than as the thing SPIFFE replaces. The draft also carries a requirement worth auditing against: a credential for internal platform access should not be reused to federate to an external STS, because that conflates trust and audience boundaries. This mesh mints a separate token per destination — the service URL for GCP, sts.amazonaws.com for AWS, api://AzureADTokenExchange for Entra — so it passes, because the audiences were picked deliberately.

Transaction Tokens, draft 08, March 2026, OAuth working group, cover the other half. Short-lived signed JWTs carrying user identity, workload identity and authorization context along a call chain, issued by a Transaction Token Service implementing a profile of the OAuth 2.0 Token Exchange endpoint, and cryptographically protected so downstream workloads cannot alter what they were handed or invent a call no transaction started.

This is the microservices industry having already learned the lesson. Passing the caller's access token down the chain does not work. The fix was a separate token for the chain, not a better credential for the workload. There is an Agent extension, Transaction Tokens for Agents by Ashay Raut at Amazon, using sub for the principal and act for the Agent acting; draft 06 expired in April 2026 and was replaced by an individual submission.

Alongside those: SPIFFE Federation, A2A's own extension mechanism, and on the research side Authorization Propagation in Multi-Agent AI Systems (Krti Tallam, May 2026), which formalises the problem, names transitive delegation, aggregation inference and temporal validity as sub-problems, derives seven structural requirements, and concludes the field is "converging on the problem, but not yet on a complete architecture." OIDC-A proposes an OIDC extension with delegation chains and attestation evidence, as an individual proposal rather than an adopted specification.

Tier two — the governance frameworks, which say what and not how

A large body of work exists here and it is easy to miss because it is written for security programmes rather than for engineers.

  • The Cloud Security Alliance has Agentic AI Identity and Access Management: A New Approach, an Agent Identity Governance Framework, and a whitepaper on the non-human identity governance vacuum.
  • The OWASP Top 10 for Agentic Applications 2026 treats Agents as operational actors with delegated authority, and two of its categories are Identity and Privilege Abuse and Insecure Inter-Agent Communication.
  • NIST issued a Request for Information on AI Agent Security in early 2026 and a concept paper on AI Agent Identity and Authorization. It points toward decentralised identifiers and verifiable credentials without mandating a technology.

These are useful for deciding what to require. None of them tells you which token to put in which header, which is the question you have when the far side is a different vendor.

Tier three — the products, and this is where cross-Cloud actually shows up

All three Clouds shipped Agent identity in 2026, which is the part I had not accounted for.

Vendor Agent identity, 2026
ProductStatusShape
Bedrock AgentCore Identity GA Built on Cognito. Inbound authorizer plus an outbound token vault for downstream tools.
Microsoft Entra Agent ID Preview Agents as first-class directory objects, under Conditional Access and the same lifecycle controls as users.
Vertex AI Agent Engine identities Shipped Agent identities inside Google's agent runtime.

And they do address cross-Cloud — bilaterally. Microsoft documents securing a Bedrock Agent with Entra Agent ID and surfacing Agents from Bedrock, Vertex and Databricks in one registry. AWS documents Entra as an inbound identity provider for AgentCore Runtime and Gateway, configured with a discovery URL and a list of accepted aud claims.

Every one of those is a vendor integration, not a federation. Each Cloud keeps its own registry and its own mapping, and cross-Cloud works because one vendor decided to support another. There is no interoperable registry and no neutral protocol — which is the same structure as the trust policies underneath, one layer up.

Two details from the AgentCore documentation are worth reading closely, because they cut against the discourse these products are sold into.

Its Entra inbound path supports "v1.0 and v2.0 Access and ID tokens that do not have any custom claims." The one leg in this mesh that lets you bring your own issuer documents that path as not carrying the extra claims a delegation chain would need.

And the outbound Microsoft credential provider is configured like this:

{
  "name": "NAME",
  "credentialProviderVendor": "MicrosoftOAuth2",
  "oauth2ProviderConfigInput": {
    "microsoftOauth2ProviderConfig": {
      "clientId": "your-client-id",
      "clientSecret": "your-client-secret",
      "tenantId": "your-microsoft-entra-tenant"
    }
  }
}

A stored client secret, in the Agent identity product, for the cross-Cloud leg. This mesh does that leg with a federated credential and no secret at all.

What the three tiers add up to

Plenty has been written. The protocol work splits credential from call chain and is mostly at draft. The governance work says what to require and not how. The products are real and shipping, and each one is a single Cloud's registry with bilateral integrations bolted on.

The gap is specific: there is no neutral cross-Cloud Agent identity, and the direction of travel is three vendor planes rather than one standard. Which puts the architecture question back where it started — what do you build on top of three trust domains you do not control.

SPIRE Answers the First Half

Put SPIRE against that split and it is a credential system. A good one, for meaning A. It says nothing about a call chain, and the delegation problem these articles open with sits entirely in the second half.

Which leaves the practical objections, and there are three.

It removes none of the federation work

Every Agent in this mesh consumes external OIDC and carries on doing so. AWS still needs a trust policy, Entra still needs a federated credential, Cloud Run still needs an invoker binding. SPIRE changes which issuer those three trust. It does not reduce their number, and configuring them is the work.

It also changes the shape of that configuration. Google is a native AWS identity provider, so you must not create an IAM OIDC provider for it — doing so breaks federation:

"Principal": { "Federated": "accounts.google.com" },
"Condition": { "StringEquals": {
    "accounts.google.com:oaud": "sts.amazonaws.com",
    "accounts.google.com:sub":  "<service account numeric ID>"
}}

SPIRE is not native, so the IAM OIDC provider becomes required and the conditions key on a discovery domain you host:

"Principal": { "Federated":
    "arn:aws:iam::012345678901:oidc-provider/oidc-discovery.example.org" },
"Condition": { "StringEquals": {
    "oidc-discovery.example.org:aud": "mys3",
    "oidc-discovery.example.org:sub": "spiffe://example.org/ns/default/sa/default"
}}

Opposite rules for two tasks that look identical on a diagram.

There is nowhere to put the Agent, and the project knows

There is an RFC for serverless support, spiffe/spire#1843, proposing an agentless path where the function attests directly to the Server. Opened September 2020. Still a proposal.

What it proposes to attest with is the part to read:

  • For Google Cloud Functions, validate the identity token from the Compute Metadata Server.
  • For AWS Lambda, sign a GetCallerIdentity query with SigV4 and let the Server replay it.

Those are the two primitives this framework already calls directly. The coordinator mints the metadata token itself, and running the coordinator on AWS instead already signs a GetCallerIdentity request and hands it to Google's STS. On serverless, SPIRE's own design is a wrapper around what the mesh does today.

The one argument that does land

AWS has the field these articles keep asking for. SourceIdentity is set once, cannot be changed, survives role chaining, and appears on every action taken with the role. Session tags do the same for attributes.

Both are filled from claims inside the web identity token, not from a request parameter. The caller cannot set them. The identity provider has to, and the GCE metadata identity endpoint takes three query parameters, which is the whole surface:

GET /computeMetadata/v1/instance/service-accounts/default/identity
      ?audience=<your audience>
      &format=full
      &licenses=FALSE

The claim set is fixed: issuer, issued-at, expiry, audience, subject, authorized party, email, verified flag, and a Compute Engine block under format=full. No parameter adds one. Two of the three Clouds would accept a delegation chain and none of the three legs can send one, because they all start at a minter with no way to say anything beyond an audience.

Run the Server yourself and the claim set is yours. That is a real gain and it does not shrink as the mesh gets smaller. It is also not what "adopt SPIFFE for workload identity" is selling, because you already have workload identity. The gap is claims, and claims have cheaper answers than a CA.

But You Could Make It Work

You could, and the design deserves writing out, because it is the obvious response to everything above.

Nobody says the SPIRE Agent has to run on the serverless runtime. Only the caller needs an identity and there is one caller. So run the Server on a VM or a small GKE cluster. Have the coordinator present its Cloud Run metadata token to the Server and get back a JWT-SVID carrying whatever claims you want. Publish the JWKS through the OIDC Discovery Provider, point the AWS and Entra trust policies at it, and you have one SPIFFE ID and full control of the claim set.

That works on a whiteboard. Here is what each part costs.

The SVID is asserted, not attested

SPIFFE's value is attestation — an identity bound to something observed about the workload. In this design the Server observes nothing. It receives a Google token and re-signs its claims under a new name.

The SPIFFE ID then means exactly what the Google token meant, because that is the only evidence in the chain. You have not added attestation. You have added a signing hop and a private key to look after, so the identity is weaker than the one it wrapped.

It creates a new secret zero, and it is the best one in the building

The CA signing key becomes the most valuable secret you own. Take it and you mint identities that AWS and Entra accept for your roles, and the metadata server they think they are trusting is never consulted.

The goal of this whole exercise was no long-lived secrets anywhere in the mesh. Today there are none. Google holds the signing key, and if that key is compromised it is Google's problem and everyone's problem at once. Adopting SPIFFE to remove secret zero would introduce a new one, more valuable than any it removed, on infrastructure you patch yourself.

The GCP leg cannot use it

Cloud Run's invoker check validates Google-signed ID tokens. It does not take an arbitrary external issuer, so a JWT-SVID is not a credential that leg can use.

Two ways round it, neither good. Skip that leg and you run SPIFFE for two Clouds while the third keeps Google tokens — more mechanisms than you started with. Or exchange the SVID back into a Google credential through Workload Identity Federation, which means minting a Google token, converting it to an SVID, then converting it back.

The pinning does not collapse to one

Count the places again after adopting it:

  • AWS — an IAM OIDC provider, plus a trust policy naming the SPIFFE ID
  • Entra — a federated credential naming issuer and subject
  • GCP — a workload identity pool and provider, or the invoker binding
  • SPIRE — registration entries, a fourth registry that did not exist before

A trust domain unifies the format of an identity. It does not reduce the number of far ends that decide what the identity may do, because that decision belongs to each of them and cannot be delegated to your Server.

SPIFFE Federation is not the escape hatch

The usual reply is that SPIFFE has federation built in, so let the trust domains federate.

The SPIFFE Federation specification defines an exchange of trust bundles between trust domains, each publishing an HTTPS bundle endpoint the other polls. No identities are delegated and no keys are shared — the domains learn to verify each other's SVIDs and nothing more.

That needs the far side to be a SPIFFE trust domain publishing a SPIFFE bundle endpoint. AWS is not one. Neither is Azure, nor Google. Federation is available exactly when both parties already run SPIFFE, which is meaning A again.

It puts one endpoint you host in front of all three legs

This is the one I would refuse on even if the others were solved.

AWS and Entra validate a JWT-SVID by fetching your JWKS over the public internet. Every cross-Cloud call in the mesh then depends on a discovery endpoint you run, on DNS you manage, behind a certificate you renew.

A multicloud mesh whose auth funnels through one self-hosted endpoint is not multicloud where it counts. Today the three legs fail independently — each depends on its own vendor's identity service, and no single outage takes all three. Add the discovery provider and you have three independent dependencies plus one shared one sitting in front of them.

Multicloud is supposed to buy independence. This spends it.

None of these are objections to SPIFFE. They are objections to bolting a token exchange onto a substrate the design was not drawn for.

Where SPIRE is the Right Call

Meaning A, and not grudgingly. Inside a boundary you control, SPIRE does something the Clouds do not do for you.

  • Your Agents run on Kubernetes. Nodes exist, the k8s node attestor works, and every objection above except the operational one disappears.
  • You have a lot of identities. Past a dozen across three Clouds, verifying pinnings by hand stops working and one trust domain starts paying for itself.
  • You need workload-to-workload mTLS. X.509-SVIDs beat anything you would assemble from three Clouds' primitives.

None of those describe a serverless Agent mesh calling managed runtimes on three vendors.

What a Valid Alternative Looks Like

Follow the split the standards already made. A credential identifies the workload. A separate token carries the chain. Four layers, each with a specification behind it, none needing a node.

Layer 1 — who is calling

Platform workload identity, per destination

Keep the metadata mint. It is attested by the only party positioned to attest anything on serverless, costs nothing to run, and WIMSE documents it as an established pattern rather than a shortcut.

Enforce audience separation: one token per destination, never a platform-internal credential reused against an external STS. That is what stops a token minted for one boundary being replayed at another.

Layer 2 — on whose behalf, through whom

A transaction token for the call chain

The layer this mesh does not have, and the one the Agent-identity articles are really asking for. A Transaction Token Service sits at the edge, takes the incoming request and whatever authenticated the requester, and issues a short-lived signed JWT with sub for the principal and act for the Agent acting. Each Agent presents it and requests a new one to call the next hop, so the chain accumulates instead of being asserted.

Two properties make this the right shape. The token is immutable in transit, so a downstream Agent cannot widen the context it was handed or fabricate a transaction that never started. And it is separate from the credential, so it is unaffected by three Clouds each dictating their own credential format.

The Txn-Token Service is something you run. It is not in the credential path. If it is down you stop starting new work; you do not lose the ability to authenticate, and no Cloud is fetching keys from you to validate a login.

Layer 3 — carried by the protocol

A2A message metadata, not the credential

The transaction token travels in the A2A message. The extension mechanism added in v1.0.1 is the sanctioned place, and the Secure Passport extension already defines a CallerContext attached beside the task with a client identifier, state and a signature.

Use the extension as the envelope and a transaction token as the payload and the two gaps cancel. Secure Passport supplies a standard carrier every A2A implementation can be taught to read. The transaction token supplies the delegation semantics and signing model Secure Passport leaves open.

Declare it on the Agent Card as well. A2A carries securitySchemes in OpenAPI 3 shape plus a security block mapping scopes to individual skills, so a client learns what an Agent requires by reading rather than by failing. Most deployments, this one included, declare far less than the spec allows.

Layer 4 — narrowing, per hop

Attenuate where the Cloud supports it

Where a Cloud lets you narrow a credential below what the role permits, do it per call rather than per deployment. On the AWS leg an inline session policy on AssumeRoleWithWebIdentity intersects with the role and can never widen it, so a session can be scoped to the single action a hop needs.

Measured on this mesh: narrow the session to card discovery and the invocation is refused; narrow it to invocation and the card fetch is refused first. Both refusals name the session policy as the layer that said no. This is the one rule of the three a deployment can demonstrate rather than assert.

Why this beats bolting on SPIRE

Layer 1 is free and already attested. Layer 2 is a service you run, outside the credential path, so its failure mode is no new work rather than no authentication anywhere. Layer 3 is protocol machinery that already exists. Layer 4 is a request parameter.

The SPIRE design puts a service you run and a public discovery endpoint inside the credential path for all three legs, to obtain claim control that layer 2 provides without touching credentials at all.

Transaction Tokens are at draft 08 and the Agent extension is an individual submission. Layers 1, 3 and 4 are available today regardless of what happens to layer 2, and the decomposition holds either way.

The two-afternoon version

If none of that is happening this quarter, the useful subset is small.

Put a requester field on the run record. Until a run carries who asked for it, the audit trail names the coordinator as the actor for everything — the original complaint in every one of these articles, fixable in an afternoon with no new components.

Then use RoleSessionName. Required on every AssumeRoleWithWebIdentity call, caller's choice, two to sixty-four characters, and it lands in the assumed-role ARN and in CloudTrail. It is the only caller-supplied identity string in this mesh that reaches a Cloud provider's audit log, and it is currently a constant. A run correlator there makes a CloudTrail entry traceable to a specific run, for one extra STS call per run.

Two I would not start with

Running your own OIDC issuer gets you claim control and makes you an identity provider. Key custody, rotation and availability become yours, and you inherit the public-endpoint failure mode without the attestation that justified it.

A single egress broker holding all three federations builds the target you least want. This project's own coordinator was open to the internet on a public invoker binding with three sets of federated credentials behind it. A broker makes that surface the architecture rather than the accident.

Summary

Three Agents are deployed across GCP, AWS and Azure with a coordinator on Cloud Run, federating three ways with no stored secrets and eight controls confirming it. The protocol never needed a change. The auth strategy took the effort and is what would break first.

SPIFFE and SPIRE are the default recommendation for that strategy and they solve the other multicloud problem — identity for workloads inside a boundary you control. An Agent mesh is the case where you own one end and three vendors dictate the rest. SPIRE removes none of the federations, adds a Server and a public endpoint, and needs a node to attest that serverless runtimes do not have.

The deeper reason is that a Cloud identity has no meaning outside its Cloud. AWS checks Google's signature and then applies a rule you wrote about a number it has never seen. Every far end decides locally what a foreign identity may do, so the mapping exists once per boundary no matter who issues the token. Change the issuer and you have changed the signature, not the arithmetic.

What is missing is narrower than the articles suggest, and the standards bodies have already divided it correctly. A credential identifies the workload and the Clouds hand you an attested one for free. A separate token carries the call chain, because that context cannot survive inside a credential three vendors each define differently. WIMSE is standardising the first half, OAuth Transaction Tokens the second, and A2A's extension mechanism is where the second one travels.

The thing to watch is that the Clouds are not waiting for any of it. AWS, Microsoft and Google all shipped Agent identity in 2026, each as a registry inside its own boundary, and cross-Cloud works where one vendor has chosen to support another. AWS accepts Entra as an inbound provider; Microsoft surfaces Bedrock and Vertex Agents in its registry. Useful integrations, and the same structure as the trust policies underneath — a local decision at each boundary, made bilaterally, one layer higher up.

That is the argument for keeping the credential layer boring. Federation you configure yourself works the same on every Cloud and does not move when a vendor changes which competitor it supports this quarter.

And if one thing were to change, it is smaller than any of the proposals. Three Clouds is six directed edges and four Clouds is twelve, because each edge is settled separately by what the caller presents and what the callee accepts. Make every ingress accept an OIDC discovery URL, an audience and a subject condition — which AgentCore already does — and the matrix collapses from N² to N. Three mints, three accept-configurations, and a fourth Cloud costs one of each. No new identity format, no neutral issuer, no CA to run. Just two more products dropping a restriction that one of them has already dropped.
