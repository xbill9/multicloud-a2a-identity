Does SPIRE Fit Cross-Cloud A2A?

The benchmark series put Agents on GCP, AWS and Azure and timed the calls between them. This article asks a different question about the same framework: should the identity layer be SPIFFE and SPIRE, or is the platform already doing the job?

Why Ask This Now?

The earlier articles were about speed. Auth was whatever it took to get the call to connect.

That order is fine for a benchmark and wrong for anything else. There is a lot of writing at the moment saying Agents need a real identity layer, and most of it lands on the same recommendation: use SPIFFE and SPIRE. Jitendra Gupta's article on Agent identity is the clearest version I have read.

The recommendation is usually made in the abstract. I already have the mesh deployed, so this article works out what adopting SPIRE would actually mean for it — what you would install, what you would delete, and what you would get that you do not have now.

What are SPIFFE and SPIRE?

SPIFFE is the specification. It gives every workload an ID that looks like a URI — spiffe://example.org/coordinator — and defines two credential formats that carry it: an X.509-SVID for mTLS, and a JWT-SVID for anything that wants a bearer token.

SPIRE is the implementation. It has three moving parts:

  • SPIRE Server. One per trust domain. Signs SVIDs, holds the registration entries, needs a datastore and an HA story.
  • SPIRE Agent. Runs on every node next to the workloads. It attests the node to the Server, then attests each local workload and hands it an SVID over a Unix socket.
  • OIDC Discovery Provider. Publishes the JWKS so an outside Cloud can validate a JWT-SVID. This is the piece that makes cross-Cloud federation possible.

The important structural point is the middle one. SPIRE's whole trust model starts with a node it can attest.

What Does the Framework Already Do?

The coordinator runs on Cloud Run and calls three Agents. Every outbound leg starts at the same place — the metadata server issues a short-lived OIDC token with whatever audience you ask for — and then diverges by Cloud:

GCP → GCP Google ID token, audience pinned to the service URL
GCP → AWS Token to STS AssumeRoleWithWebIdentity, then SigV4
GCP → Azure Token to an Entra Federated Identity Credential

There are no stored secrets on any of those legs. Each one has a positive control and a negative control — run it as deployed, then run it with the credential removed and check it gets refused. Eight probes, all holding on the current build.

So the framework already has the thing SPIFFE exists to provide. The metadata server issues a short-lived, audience-scoped token that the platform vouches for and the workload cannot forge. That is the same class of object as a JWT-SVID, and the trust conditions on AWS and Azure are written against its subject.

So Why Would I Need SPIRE? Can't I Just Use the Metadata Server?

For a three-leg mesh, mostly yes. There are two real arguments against, and they are worth separating because only one of them is about scale.

Argument one: the identity is pinned in three places

The coordinator has one identity — a service account with a numeric ID. That number is written down three times, in three vendors' formats: as a condition in an AWS trust policy, as the subject on an Entra federated credential, and as an IAM binding on Cloud Run.

Nothing keeps those three in sync. The Azure deploy script has a verify step that reads the federated credential back and compares it to the service account, which exists because the two can drift apart. At three pinnings you can check them by hand. At thirty you cannot, and that is the case SPIRE is built for: one trust domain, one ID, and the Clouds trust the Server instead of each holding their own copy.

Argument two: you do not control the claims

This is the one that surprised me, and it is not about scale at all.

AWS already has the field the Agent-identity articles are asking for. SourceIdentity is set once, cannot be changed, survives role chaining, and appears on every action taken with the role. Session tags do the same job for attributes. If you want to know which Agent relayed a call, AWS will record it.

Both are filled from claims inside the web identity token. Not from a request parameter — the caller cannot set them. The identity provider has to.

And on this framework the identity provider will not. The GCE metadata identity endpoint takes three query parameters:

GET /computeMetadata/v1/instance/service-accounts/default/identity
      ?audience=<your audience>
      &format=full
      &licenses=FALSE

That is the whole surface. The claim set that comes back is fixed: issuer, issued-at, expiry, audience, subject, authorized party, email, verified flag, and a Compute Engine block when you ask for format=full. There is no parameter that adds a claim.

Two of the three Clouds would accept a delegation chain. None of the three legs can send one, because they all start at a metadata server that has no way to say anything beyond an audience.

SPIRE changes that, and this is the strongest technical argument for it here. When you run the Server, the claim set is yours. The documented SPIRE-to-AWS pattern uses session tags on AssumeRoleWithWebIdentity, which is exactly the field the metadata server cannot reach.

Where Does the SPIRE Agent Actually Run?

This is where the idea meets the framework, and it is a straight architectural mismatch rather than a matter of effort.

The three runtimes in this mesh are Cloud Run, Bedrock AgentCore and Azure Container Apps. None of them gives you a node. You cannot run a daemon on the host, because there is no host you can address, and the containers come and go per request.

The SPIFFE project knows this. There is an RFC for serverless support — spiffe/spire#1843 — proposing an agentless path where the function attests directly to the Server. It was opened in September 2020. It is still a proposal.

What that RFC proposes is worth reading closely, because of what it plans to attest with:

  • For Google Cloud Functions, validate the identity token from the Compute Metadata Server.
  • For AWS Lambda, sign a GetCallerIdentity query with SigV4 and let the Server replay it.

Those are the two primitives this framework already calls directly. The coordinator mints the metadata token itself, and the reverse direction — running the coordinator on AWS — already signs a GetCallerIdentity request and hands it to Google's STS as a subject token. On serverless, SPIRE's own plan is to wrap what the mesh is doing today.

The Trust Policy is Not the Same Shape

One more thing to know before you cost this out. Federating to AWS from SPIRE is not the same configuration as federating from Google, and the difference is the kind that produces a confusing failure rather than a clear one.

Google is a native AWS identity provider. You do not create an IAM OIDC provider for it — if you do, federation stops working. The trust policy names the principal directly:

"Principal": { "Federated": "accounts.google.com" },
"Condition": { "StringEquals": {
    "accounts.google.com:oaud": "sts.amazonaws.com",
    "accounts.google.com:sub":  "<service account numeric ID>"
}}

SPIRE is not native, so you must create the IAM OIDC provider, and the conditions are keyed on your own discovery domain:

"Principal": { "Federated":
    "arn:aws:iam::012345678901:oidc-provider/oidc-discovery.example.org" },
"Condition": { "StringEquals": {
    "oidc-discovery.example.org:aud": "mys3",
    "oidc-discovery.example.org:sub": "spiffe://example.org/ns/default/sa/default"
}}

Opposite rules for two tasks that look identical on a diagram. Worth writing on the runbook either way.

The discovery domain in that second policy is also a real deliverable. AWS and Entra fetch the JWKS over the public internet, so the OIDC Discovery Provider needs a DNS name, a certificate, and an endpoint you keep reachable. Losing it does not degrade the mesh gracefully — every leg stops federating.

Read the fourth row twice, because it is the one people skip. SPIRE does not replace the federations. Every Agent in this mesh consumes external OIDC and will carry on doing so — AWS still needs a trust policy, Entra still needs a credential, Cloud Run still needs an invoker binding. You add a Server, an Agent, a public endpoint and a certificate, and you keep all three federations. What you remove is the duplication of one number across them.

So Does it Make Sense?

Not for this framework as it stands. Three reasons, in order of how much they matter:

  1. There is nowhere to put the Agent. All three runtimes are serverless, and the agentless path has been a proposal since 2020.
  2. The gain is deduplication of three pinnings. Three is a number you can verify with a script, which the deploy already does.
  3. You would be swapping a managed minter with no operational cost for one you run, and adding a public endpoint whose outage takes down all three legs at once.

The claims argument is real and it is the one I would revisit first. But it buys you something the framework has no use for yet: there is no human in this mesh, no requester on a run, and one hop between coordinator and Agent. A delegation chain needs something to chain.

When Would it Make Sense?

Three conditions, any one of which flips the answer:

  • The Agents move to Kubernetes. On EKS, GKE or AKS you have nodes, the k8s node attestor works, and every objection above except the operational one disappears.
  • The pinning count gets away from you. Somewhere past a dozen identities across three Clouds, hand-verification stops working and one trust domain starts paying for itself.
  • You need claims the Cloud minters will not give you. If a person is initiating work and you have to record who, controlling the minter is the shortest route to it.

None of those are true here today. All three are plausible within a year.

What I Would Do Instead

The cheap half of the delegation problem needs none of this.

RoleSessionName is required on every AssumeRoleWithWebIdentity call. Two to sixty-four characters, caller's choice, and it lands in the assumed-role ARN and in CloudTrail. It is the only caller-supplied identity string in this mesh that reaches a Cloud provider's audit log, and it is currently set to a constant. Putting a run correlator there would make a CloudTrail entry traceable to a specific run. The cost is one STS call per run rather than one per process.

And before any of that, the run record needs a requester field. Until a run carries who asked for it, the audit trail names the coordinator as the actor for everything — which is the original complaint in all these articles, correctly aimed, and fixable without a new identity system.

Summary

Three Agents are deployed across GCP, AWS and Azure with a coordinator on Cloud Run, federating three ways with no stored secrets and eight controls confirming it.

Against that framework, SPIFFE and SPIRE do not currently fit — the runtimes are serverless and SPIRE needs a node to attest, and the agentless design for that has been open since 2020. The gain on offer is collapsing three copies of one identity into one trust domain, which is a scale argument that this mesh has not reached.

The argument that would change my mind is not scale. It is claims: SPIRE lets you decide what goes in the token, and the metadata server does not. That matters the moment a person is in the chain, and it does not matter until then.
